## Принятая архитектура

```text
Браузер → Next.js SSR → GET Bitrix /api/v1/home → Zod → HTML
```

- Production — Node.js с Next.js App Router, не статический экспорт.
- Bitrix, PHP и база разворачиваются отдельно; Next.js не обращается к БД.
- `src/lib/bitrix/home.ts` — server-only адаптер с `cache: 'no-store'`.
- При новом запросе страницы изменения CMS должны попадать в HTML без сборки.
- Для переключения нужны runtime-переменные `CONTENT_SOURCE=bitrix` и
  `BITRIX_API_URL`, содержащая полный URL `/api/v1/home`.
- В текущем `.env.local` стоит `CONTENT_SOURCE=demo`. Compose также использует
  demo по умолчанию. Успешная сборка не доказывает подключение к CMS.
- Вызов `connection()` исключает загрузку контента во время production build.
- `cms/local/api/home.php` и `cms/.htaccess` — проектный PHP-адаптер и rewrite.
  Внутренние поля инфоблоков остаются на стороне CMS.
- Формы должны использовать отдельный D7 endpoint `POST /api/v1/leads`.
  Его реализации в отслеживаемом коде пока нет.

## Что блокирует полноценный запуск

1. **Заявки не отправляются.** В `BookingSubmission.tsx` кнопка disabled,
   обе формы вызывают `preventDefault()`. `submit-lead.ts` нигде не вызывается.
   Сохранённый helper отправляет только имя, телефон и согласие; он не передаёт
   тариф, сценарий, участников, дату, аудиторию или ответы квиза. В репозитории
   нет ни PHP lead endpoint, ни Next route/proxy для относительного URL
   `/api/v1/leads`. Нужно определить маршрут до отдельного Bitrix, завершить
   контракт, серверную валидацию, защиту от спама, сохранение/доставку заявки,
   состояния отправки, успеха и ошибки и проверить весь путь.
2. **Квиз не завершает подбор.** Ответы живут в локальном state; на последнем
   вопросе кнопка «далее» отключается. Нет результата, завершения и передачи
   ответов в форму или заявку.
3. **SEO остаётся демонстрационным.** Глобально установлен `noindex, nofollow`,
   `metadataBase` указывает на demo-домен, title и description шаблонные.
   Все три страницы наследуют одинаковые metadata и H1.
4. **Контакты имеют разные источники.** В коде указаны Домодедово и телефон
   с кодом 495, в demo-контенте и OG — Саратов. Карту также определяют жёстко
   заданные координаты. Нужно подтвердить фактический регион и объединить
   контакты, координаты, маршрут, соцсети и SEO в согласованные данные.
5. **Публичные материалы не завершены.** Соцсети ведут на `#footer`, кнопка
   «Как проехать» отключена. Текст согласия упоминает политику, но ссылки и
   отдельной страницы/файла политики в текущем frontend нет.
6. **Последние изменения ещё не зафиксированы.** На старте аудита изменены
   11 отслеживаемых файлов, не отслеживаются шесть новых WebP и
   `src/lib/scroll-scenes.ts`. Текущая локальная сборка использует эти файлы;
   перед сборкой из Git их нужно включить в релиз.

## SEO, управляемое из Битрикс

Недостаточно настроить SEO-поля в Bitrix: публичный HTML формирует Next.js.
Нужен путь «поля CMS → JSON → Zod → `generateMetadata` и контент страницы».

Для каждой из трёх страниц предлагается отдельная SEO-запись:

| Поле                                                | Назначение                                               |
| --------------------------------------------------- | -------------------------------------------------------- |
| `title`                                             | Заголовок страницы в metadata                            |
| `description`                                       | Описание страницы                                        |
| `h1`                                                | Видимый заголовок; хранить отдельно от title             |
| `canonicalPath`                                     | Канонический путь; по умолчанию собственный URL страницы |
| `noindex`, `nofollow`                               | Управление индексацией отдельной страницы                |
| `ogTitle`, `ogDescription`, `ogImage`, `ogImageAlt` | Карточка ссылки с fallback на основные SEO-поля          |

Вне отдельных страниц нужны общий production URL из конфигурации окружения,
название клуба, реальные контакты, координаты, часы работы и ссылки на профили.
На их основе можно формировать JSON-LD организации/площадки. Разметку собирать
из типизированных данных, не хранить произвольный HTML или JavaScript в SEO-полях.

Дополнительно перед релизом:

- Добавить `robots.txt`, `sitemap.xml`, favicon; в sitemap включать
  канонические индексируемые страницы.
- Открывать индексацию только на production; тестовые окружения сохранять
  закрытыми независимо от редакторских настроек.
- Уникализировать title, description и тексты аудиторных страниц.
- Подключить проверочные коды поисковых сервисов и аналитику, если нужны,
  и определить события успешной заявки, клика по телефону и завершения квиза.
- Синхронно менять PHP-ответ, Zod, demo payload и примеры в документации:
  текущий `z.strictObject` отвергнет незнакомые поля, добавленные только в PHP.

Документация: [Next.js Metadata](https://nextjs.org/docs/app/getting-started/metadata-and-og-images),
[Google JavaScript SEO](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics),
[Google LocalBusiness](https://developers.google.com/search/docs/appearance/structured-data/local-business).

## Надёжность и производительность

- CMS fetch не имеет явного timeout; ошибки сети, HTTP и Zod уходят в ошибку
  страницы. Нет собственного `error.tsx`/`global-error.tsx`. Нужны ограничение
  ожидания, понятный экран ошибки и серверные логи. Политику fallback выбирать
  отдельно; автоматически подменять production демо-данными не следует.
- Квиз обязателен в PHP и Zod: пустой квиз делает недоступной всю страницу.
  Стоит решить, какие секции действительно обязательны для рендеринга сайта.
- У карты нет видимого fallback при ошибке внешнего API. Проверить её работу
  на production-домене и показать адрес/ссылку на маршрут при сбое.
- `images.unoptimized: true` осознанно оставляет подготовку картинок на проекте.
  Самый крупный hero для mobile — PNG 1,78 МиБ; кандидат на WebP/AVIF.
- Шрифты локальные, ролики имеют отдельные версии, видео и карта подключаются
  лениво. Это полезная уже выполненная работа.
- Нужен финальный браузерный прогон production: mobile/desktop, переходы между
  аудиториями, loader, scroll-сцены, клавиатура, reduced motion, модалки, ошибки
  CMS/карты и медленная сеть. Lighthouse/Core Web Vitals этим аудитом не измерены.
- Нет CI workflow в `.github/`; тесты календаря существуют, но не входят в
  `npm run check`. Проверка реального контракта и отправки заявок ещё нужна.
- `verify.mjs` читает `process.env`, сам не загружает `.env.local` и пропускает
  endpoint check без URL. Проверяет HTTP-успех, а не JSON по Zod, и вызывает
  обычные checks. Его PASS сам по себе не доказывает CMS-интеграцию.

   проверить сохранение/доставку и ошибки.
5. Добавить документы, реальные ссылки, SEO-файлы и обработку сбоев.
6. Исключить локальные артефакты из Docker context, нормализовать окончания
   строк и зафиксировать все файлы релиза. Убрать demo-only подключения.
7. Собрать из чистого checkout, проверить Docker/целевой хостинг с реальным
   Bitrix, прогнать браузерную приёмку и после неё открыть индексацию production.
